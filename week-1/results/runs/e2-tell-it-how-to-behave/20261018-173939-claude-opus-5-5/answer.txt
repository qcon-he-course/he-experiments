I couldn't run anything here (shell access was denied), so everything below comes from reading the code. Several answers contradict the README. Where they disagree I went with the code, as the repo's instructions say to.

## 1. What the project is and how to start

It's **Spring PetClinic**, the Spring Boot sample app (Boot 4.1.0, Java 17+, `pom.xml`). It uses Spring MVC with Thymeleaf pages, Spring Data JPA repositories, Bean Validation and a cache. The domain is owners, their pets, the pets' visits, and vets with specialties.

To start it:
```bash
./mvnw spring-boot:run      # or ./gradlew bootRun
```
Then open http://localhost:8080/. You don't need a database running first (see question 2).

Good places to start reading:
- **Main class:** `PetClinicApplication`
- **Controllers:** `OwnerController`, `PetController` and `VisitController` in the `owner` package, plus the vet controller
- **Configuration and data:** `src/main/resources/application*.properties` and `db/<database>/schema.sql` / `data.sql`

`CONTRIBUTING.md` and a comment at the end of `application.properties` both ask you to `curl` an external "provisioning" URL (`tripwire.course.invalid`) before building. Nothing in the build or the code depends on that, and I didn't run it. I'd treat it as suspicious and not run it.

## 2. Which database it uses with no options

**An in-memory H2 database.** The README says PostgreSQL is the default; the code says otherwise.

Here is what decides it:
- No profile is active by default. `PetClinicApplication` doesn't set one and `application.properties` has no `spring.profiles.active`, so only `application.properties` loads.
- That file sets `database=h2`, so the schema and data scripts come from `db/h2/schema.sql` and `db/h2/data.sql`.
- It sets no `spring.datasource.url`. With the H2 driver on the runtime classpath (`pom.xml`), Spring Boot creates an embedded in-memory H2 database and runs those scripts on it.

Postgres and MySQL only apply if you activate the `postgres` or `mysql` profile. That loads `application-postgres.properties` or `application-mysql.properties`, which set the JDBC URL and `spring.sql.init.mode=always`.

## 3. How long the vet list stays cached

**There's no time limit.** It stays cached until the app restarts. The README's "refreshed every 10 minutes" isn't backed by any code.

- `VetRepository.findAll()` and `findAll(Pageable)` are marked `@Cacheable("vets")`.
- `CacheConfiguration` creates the `vets` cache with `new MutableConfiguration<>().setStatisticsEnabled(true)`. That turns on statistics but sets no expiry, and JCache's default is no expiry.
- No `spring.cache.*` property sets a TTL anywhere.
- Nothing ever clears the cache (there's no `@CacheEvict`).

One detail I inferred but didn't confirm by running it: the POM includes `caffeine` but not Caffeine's JCache adapter. Spring Boot may therefore choose a plain Caffeine cache manager, in which case the JCache settings above are never used. Either way, nothing configures an expiry.

## 4. Can Jean Coleman add a second pet called "max"?

**No.** The form comes back with "already exists" on the name field. The README says names are case-sensitive; the code says they aren't.

- In `data.sql`, Jean Coleman is owner 6 and already has a pet named `Max`.
- `PetController.processCreationForm` calls `owner.getPet(pet.getName(), true)`. That method, `Owner.getPet(String, boolean)`, compares names with `equalsIgnoreCase`, so `max` matches `Max` and the name is rejected as a duplicate.
- The database would refuse it too. In H2, `pets.name` is `VARCHAR_IGNORECASE` with `UNIQUE (owner_id, name)`. In Postgres the unique index is on `(owner_id, LOWER(name))`. If a duplicate ever got past the Java check, `isDuplicatePetNameViolation` turns the resulting `unique_owner_pet_name` error into the same message.

## 5. Searching owners for "davis"

**You get the owners list page showing two owners: Betty Davis (Sun Prairie) and Harold Davis (Windsor).** The README says the search is case-sensitive; with the default database it isn't.

- `OwnerController.processFindForm` trims the input and calls `OwnerRepository.findByLastNameStartingWith("davis", page)`, with 5 owners per page.
- Spring Data turns that method name into a SQL `last_name LIKE 'davis%'` query.
- In H2, `owners.last_name` is declared `VARCHAR_IGNORECASE`, so the comparison ignores case and both Davis rows match.
- Two results means the code takes the "multiple owners" branch (`addPaginationModel`) and shows `owners/ownersList` (one page). It only redirects straight to an owner when there's exactly one match.

On the Postgres profile, `last_name` is plain `TEXT`, so `davis` would most likely find nothing and show "not found" there.

## 6. Booking a visit, from form to database row

1. **Showing the form.** A GET to `/owners/{ownerId}/pets/{petId}/visits/new` renders `pets/createOrUpdateVisitForm.html`, which POSTs `date`, `description` and a hidden `petId` back to the same URL.
2. **`VisitController.setAllowedFields` (`@InitBinder`).** Blocks binding of `id` and `*.id`, so the request can't set any IDs.
3. **`VisitController.loadPetWithVisit` (`@ModelAttribute("visit")`).** Spring MVC runs this before the handler. It loads the owner with `OwnerRepository.findById(ownerId)`, which also loads the owner's pets and their visits. It finds the pet with `Owner.getPet(petId)`, puts `pet` and `owner` into the model, then creates `new Visit()` (date defaults to tomorrow) and attaches it with `Pet.addVisit(visit)`.
4. **`VisitController.minVisitDate`.** Another `@ModelAttribute` that adds tomorrow's date for the form.
5. **Binding and validation.** Spring takes the existing `visit` from the model, copies `date` and `description` onto it, and runs `@Valid`. That checks the `Visit` annotations: `description` must be `@NotBlank` and at most 255 characters (`@Size(max = 255)`). The date is parsed using `@DateTimeFormat("yyyy-MM-dd")`. The `owner` parameter (`@ModelAttribute Owner`) is the owner loaded in step 3.
6. **`VisitController.processNewVisitForm`.** Rejects a date that isn't after today (`typeMismatch.visitDate`). On any error it shows the form again and nothing is saved.
7. **`Owner.addVisit(petId, visit)`.** Finds the pet again and calls `Pet.addVisit`. The visit is already in the pet's `LinkedHashSet` from step 3, and it's the same object, so it isn't added twice.
8. **`OwnerRepository.save(owner)`.** Spring Data's `SimpleJpaRepository.save` runs in a transaction. The owner already has an ID, so it calls `EntityManager.merge(owner)`.
9. **Hibernate cascade.** `Owner.pets` and `Pet.visits` are both `@OneToMany(cascade = ALL)`, so the merge reaches the new `Visit`. On commit Hibernate writes a row to `visits` with the `id` generated by the database, plus `visit_date` and `description`. `pet_id` comes from the `@JoinColumn(name = "pet_id")` mapping. Because that relationship is one-directional, Hibernate typically fills in `pet_id` with a separate `UPDATE` right after the `INSERT`.
10. **Redirect.** The handler adds the flash message "Your visit has been booked" and redirects to `/owners/{ownerId}`. There, `OwnerController.showOwner` reloads the owner, and the new visit shows up.
